# sberazs-bot

Личный Telegram-бот для мониторинга наличия топлива на АЗС через
неофициальный API sberazs.ru.

## Архитектура

Мощный сервер (парсит) находится **за NAT** и не может принимать
входящие соединения. Лёгкий арендованный сервер (с ботом) имеет белый
IP. Поэтому направление связи развёрнуто: **скрапер сам стучится к
боту**, а не наоборот.

- **Сервер-скрапер** (мощный, за NAT) — парсит sberazs.ru через
  Playwright/Chromium, хранит данные локально, и сам:
  - раз в `SCAN_INTERVAL_MINUTES` пушит найденные обновления на
    `POST {LIGHT_SERVER_URL}/notifications`
  - раз в `COMMAND_POLL_INTERVAL_SEC` спрашивает
    `GET {LIGHT_SERVER_URL}/commands` — нет ли новых запросов от
    пользователей (`/scan_city`), и если есть — сканирует и отправляет
    результат через `POST {LIGHT_SERVER_URL}/command-result`

- **Сервер-бот** (лёгкий, белый IP, за tgproxy) — Telegram-бот на
  aiogram, без Chromium вообще. Держит небольшое HTTP API, в которое
  стучится скрапер, и просто передаёт данные в Telegram.

Так лёгкому серверу не нужно ничего забирать самому — он только
слушает и отвечает, а вся инициатива (и вся тяжёлая работа) — на
стороне мощного сервера.

### Альтернатива: всё на одном сервере (монорежим)

Если когда-нибудь понадобится один сервер помощнее без NAT —
`app/main.py`, `Dockerfile.monolith`, `docker-compose.monolith.yml`.

## Установка

### 1. На лёгком сервере (белый IP, с tgproxy) — разворачиваем первым

Ему нужно начать слушать раньше, чем скрапер попробует достучаться.

```bash
git clone https://github.com/ВАШ_ЮЗЕРНЕЙМ/ВАШ_РЕПО.git
cd ВАШ_РЕПО

cp .env.bot.example .env.bot
nano .env.bot
```

Впишите `BOT_TOKEN` (от [@BotFather](https://t.me/BotFather)) и
придумайте `API_TOKEN` — длинную случайную строку (например,
`openssl rand -hex 32`), общий секрет с мощным сервером.

```bash
docker compose -f docker-compose.bot.yml up -d --build
```

Проверка:

```bash
docker compose -f docker-compose.bot.yml logs -f
curl http://localhost:8080/health
```

Должно ответить `{"status": "ok"}`.

**Откройте порт 8080 в файрволе этого сервера**, если он не открыт по
умолчанию:

```bash
apt install -y ufw   # если ещё не установлен
ufw allow OpenSSH
ufw allow 8080
ufw enable
```

### 2. На мощном сервере (за NAT) — разворачиваем вторым

```bash
git clone https://github.com/ВАШ_ЮЗЕРНЕЙМ/ВАШ_РЕПО.git
cd ВАШ_РЕПО

cp app/geoboxes_local.py.example app/geoboxes_local.py
nano app/geoboxes_local.py
```

```python
GEOBOXES = {
    "moscow": (37.3, 55.5, 37.9, 55.9),
}
```

```bash
cp .env.scraper.example .env.scraper
nano .env.scraper
```

Впишите:
- **тот же** `API_TOKEN`, что и на лёгком сервере
- `LIGHT_SERVER_URL=http://БЕЛЫЙ_IP_ЛЁГКОГО_СЕРВЕРА:8080`

```bash
docker compose -f docker-compose.scraper.yml up -d --build
```

Портов наружу открывать не нужно — этот сервер только сам ходит
наружу (к sberazs.ru и к лёгкому серверу), входящие соединения ему не
требуются, поэтому NAT ему не мешает.

Проверка:

```bash
docker compose -f docker-compose.scraper.yml logs -f
```

Ищите строки вида `Опрос команд запущен` и `Сканирую область`, без
трейсбеков вида `Connection refused`/`unauthorized` (это значило бы,
что `LIGHT_SERVER_URL` или `API_TOKEN` не совпадают).

### 3. Проверка в Telegram

Отправьте боту `/start`, затем `/scan_city moscow` (или ваш город) —
ответ придёт не мгновенно, а после того как скрапер заберёт команду
на очередном опросе (`COMMAND_POLL_INTERVAL_SEC`, по умолчанию 5 сек)
и просканирует область.

### 4. Второй бот (клон) на том же лёгком сервере

Один скрапер может отдавать одни и те же данные о станциях нескольким
ботам. Обычный сценарий: **bot** — бесплатный/основной, **bot2** —
платный клон с триалом и подпиской. Это переключается флагом
`PAYWALL_ENABLED` в `.env` каждого бота (`true`/`false`, по умолчанию
`true`) — код у обоих ботов одинаковый, просто на free-инстансе система
доступа выключена целиком: `/start` не создаёт запись триала, меню
всегда 2 кнопки («Действия»/«Подписки», без «Тариф и коины»), любые
проверки доступа считаются пройденными.

**Если у вас уже развёрнут первый бот и он должен остаться бесплатным** —
допишите в существующий `.env.bot`:

```env
PAYWALL_ENABLED=false
```

и пересоберите: `docker compose -f docker-compose.bot.yml up -d --build`.
Без этой строчки первый бот тоже останется платным (триал/подписка) —
`PAYWALL_ENABLED` по умолчанию `true`.

Данные о станциях у обоих ботов общие (один скрапер), подписчики и
доступ — у каждого свои (отдельная `bot.db`).

На **лёгком сервере** — второй бот:

```bash
cp .env.bot2.example .env.bot2
nano .env.bot2   # свой BOT_TOKEN (новый бот в BotFather) и свой API_TOKEN

docker compose -f docker-compose.bot2.yml up -d --build
```

Второй бот слушает порт `8081` (см. `docker-compose.bot2.yml`), а не
`8080`, как первый — открой этот порт в файрволе так же, как открывали
`8080` для первого бота.

На **сервере-скрапере** (`.env.scraper`) добавьте:

```env
LIGHT_SERVER_URL_2=http://БЕЛЫЙ_IP_ЛЁГКОГО_СЕРВЕРА:8081
API_TOKEN_2=тот_же_токен_что_в_.env.bot2
```

и пересоберите скрапер:

```bash
docker compose -f docker-compose.scraper.yml up -d --build
```

В логах скрапера должно появиться `Настроено ботов: 2 (bot1, bot2)`, а
`Опрос команд запущен` — по одной строке на каждого бота. Третий, четвёртый
бот и т.д. добавляются так же — `LIGHT_SERVER_URL_3`/`API_TOKEN_3`,
`docker-compose.bot3.yml` (скопируйте `docker-compose.bot2.yml` и
поменяйте порт/имя сервиса/`.env` файл).

## Команды бота

Основной интерфейс — кнопки: `/start` (или кнопка «☰ Меню» под полем
ввода) открывает короткое описание бота с тремя кнопками:

- **⚙️ Действия** — то же самое, что раньше было в `/cities`: список
  городов для мгновенного скана и отдельно — список для подписки
  (город → категория топлива). **Требует активного доступа** (триал
  или платная подписка) — иначе бот попросит открыть «💳 Тариф и коины».
- **🔔 Подписки** — список текущих подписок и кнопка «❌ Отказаться от
  всех подписок». Доступно всегда, без ограничений по подписке (чтобы
  можно было отписаться, даже если доступ закончился).
- **💳 Тариф и коины** — статус доступа (сколько осталось триала или до
  какой даты платная подписка), баланс коинов, кнопка покупки подписки
  и кнопка пополнения баланса.

Текстовые команды остаются рабочими (для скриптов/привычки), `/cities`,
`/scan_city` и `/subscribe` тоже требуют активного доступа:

- `/cities` — то же, что кнопка «⚙️ Действия»
- `/scan_city <название>` — запросить свежие станции по городу текстом
- `/subscribe [город] [категория]` — подписаться текстом
- `/unsubscribe` — отписаться от всех уведомлений
- `/my_subscriptions` — текущие подписки текстом

### Доступ: триал и платная подписка

При первом `/start` пользователю открывается пробный доступ на
`TRIAL_HOURS` часов (по умолчанию 12). Дальше — платная подписка на
`SUBSCRIPTION_DAYS` дней (по умолчанию 14) за `SUBSCRIPTION_COST_COINS`
коинов (по умолчанию 100). Повторная покупка продлевает подписку от
текущей даты окончания, а не от «сейчас» — можно продлевать заранее,
не теряя остаток. Параметры настраиваются в `.env.bot`:

```env
TRIAL_HOURS=12
SUBSCRIPTION_DAYS=14
SUBSCRIPTION_COST_COINS=100
```

**Push-уведомления о появлении топлива тоже платные**: подписка на
город/категорию (в «🔔 Подписки») сохраняется всегда, но реально
сообщения будут приходить, только пока у пользователя активен
триал/подписка — иначе рассылка на этот `chat_id` просто пропускается
(см. `handle_notifications` в `app/light_bot.py`).

**Эквайринг не подключён.** Кнопка «➕ Пополнить коины» показывает
список пакетов (`app/subscription.py::COIN_PACKAGES`, цены-заглушки —
поправьте под себя), но при выборе пакета сейчас просто показывает
текст «оплата пока не подключена» — там оставлен `TODO` с местом для
интеграции реального платёжного шлюза (сгенерировать счёт/ссылку на
оплату, а коины зачислять в вебхуке провайдера после подтверждения
оплаты, не раньше). Пока шлюза нет, начисляйте коины вручную:

```bash
docker compose -f docker-compose.bot.yml exec bot python -m app.grant_coins <chat_id> <amount>
```

`chat_id` пользователь видит сам в «💳 Тариф и коины» (строка «🆔 Ваш ID»).

### Telegram Mini App

Для платного бота (`PAYWALL_ENABLED=true`) есть Mini App — фронтенд на
чистом HTML/JS (без сборки, `app/miniapp_static/`) и REST-бэкенд
(`app/miniapp_api.py`) с 4 экранами:

1. **Сканировать области** — `GET /api/scan-targets` (области + сохранённые
   зоны), `POST /api/scan` (`{"area": "..."}` или `{"zone_id": N}`),
   `GET /api/scan-sessions/{id}` (опрос статуса — скрапер отвечает не сразу).
2. **Добавить зону** — `GET /api/catalog/areas`, `GET /api/catalog?area=...`
   (имя+адрес станций области — полный каталог, не только со свежим
   топливом), `GET/POST /api/zones`, `DELETE /api/zones/{id}`,
   `GET/POST /api/zones/{id}/stations`, `DELETE /api/zones/{id}/stations/{station_id}`.
   Зона может включать станции из разных областей.
3. **Мои оповещения** — `GET/POST /api/subscriptions`, `DELETE /api/subscriptions`
   (та же логика, что и текстовые команды бота).
4. **Тариф и коины** — `GET /api/tariff`, `POST /api/tariff/purchase`,
   `POST /api/tariff/topup` (пока заглушка — эквайринг не подключён).

**Авторизация API** — не Bearer-токен (тот только для скрапера), а
Telegram WebApp `initData`: каждый запрос фронтенда к `/api/*` несёт
заголовок `X-Telegram-Init-Data`. Статика (`/`, `/app.js`, `/style.css`)
отдаётся без проверки — initData физически недоступен странице до её
загрузки. Проверка — `app/webapp_auth.py` (официальный HMAC-алгоритм,
покрыт тестом на подмену данных и на чужой токен бота).

**Откуда берутся данные для каталога станций**: скрапер после каждого
скана области пушит на `/station-catalog` (в `light_bot.py`) полный
список известных станций этой области с именем/адресом — отдельно от
`/notifications` (те только про появление топлива). Хранится в
`station_catalog` в `bot.db` каждого бота, синхронизируется полностью
(станции, пропавшие у скрапера, удаляются и из каталога).

#### Разворачивание с доменом (DuckDNS + Caddy, порты 80/443 свободны)

Telegram требует настоящий https для Mini App — самоподписанный
сертификат не подойдёт. Если бы порты 80/443 были свободны, Caddy мог
бы получить сертификат прямо на них (HTTP-01 challenge). Но раз там уже
xray/hysteria — используем **DNS-01 challenge через DuckDNS API**:
подтверждение домена идёт через DNS (TXT-запись), никакие порты для
самого выпуска сертификата не нужны. Caddy слушает на отдельном порту
(`MINIAPP_HTTPS_PORT`, по умолчанию `8443`), 80/443 остаются полностью
у ваших xray/hysteria — Caddy их вообще не трогает и не открывает.

Для DNS-01 через DuckDNS собирается кастомный образ Caddy с плагином
(`Dockerfile.caddy`, стандартный `caddy:2-alpine` этого не умеет).

1. Заведите поддомен на [duckdns.org](https://www.duckdns.org), укажите
   у него A/AAAA-запись на белый IP лёгкого сервера. Скопируйте свой
   **token** (виден на странице duckdns.org после входа, вверху).
2. В `.env.bot2`:
   ```env
   MINIAPP_DOMAIN=findbenz.duckdns.org
   DUCKDNS_TOKEN=<ваш токен с duckdns.org>
   MINIAPP_HTTPS_PORT=8443
   MINIAPP_URL=https://findbenz.duckdns.org:8443
   ```
3. Откройте порт `8443` (или тот, что укажете) в файрволе сервера — это
   единственный порт, который нужен Mini App. 80/443 трогать не нужно.
4. Поднимите:
   ```bash
   docker compose -f docker-compose.bot2.yml up -d --build
   ```
   Сборка Caddy с плагином (`caddy:2-builder-alpine` + `xcaddy`) займёт
   пару минут при первом запуске. Сертификат через DuckDNS обычно
   выпускается за 10–30 секунд после старта — проверьте
   `docker compose -f docker-compose.bot2.yml logs -f caddy`, там будет
   видно `certificate obtained successfully`.
5. Проверка: `https://findbenz.duckdns.org:8443` должен открыть само
   приложение (вне Telegram покажет баннер «открой через бота» — это
   нормально, initData там взять неоткуда).
6. В боте `bot2` появится кнопка «📱 Открыть приложение» в главном меню
   (`/start`) — она есть только когда `MINIAPP_URL` задан.

Порт в адресе (`:8443`) — это нормальная часть https-ссылки, Telegram
открывает Mini App как обычный URL, нестандартный порт ему не мешает.
Кнопка — обычная inline-кнопка с `web_app`, регистрировать домен через
BotFather для неё не нужно (это требуется только для persistent Menu
Button через `/setmenubutton`, мы его не используем).

**Если позже порты 80/443 освободятся** — можно вернуться на
HTTP-01/обычный 443: в `Caddyfile` убрать блок `tls { dns duckdns ... }`
(тогда Caddy сам возьмёт HTTP-01 на 80), сайт-блок сделать без порта
(`{$MINIAPP_DOMAIN} { ... }`), в compose вернуть `"80:80"`/`"443:443"`,
а `MINIAPP_URL` — без `:8443`. Собранный кастомный образ Caddy при этом
мешать не будет, плагин duckdns просто не используется.

### Рассылка сообщения всем пользователям

Список получателей — все, кто хоть раз писал боту (таблица `users` в
`bot.db`, никак не связана с подписками на топливо). Запускается на
лёгком сервере:

```bash
docker compose -f docker-compose.bot.yml exec bot python -m app.broadcast "Текст сообщения"

# из файла (удобно для длинного текста, поддерживается HTML-разметка):
docker compose -f docker-compose.bot.yml exec bot python -m app.broadcast --file /app/data/message.txt

# без HTML-разметки:
docker compose -f docker-compose.bot.yml exec bot python -m app.broadcast --plain "Просто текст"
```

## Важные нюансы

- **Порядок запуска важен**: сначала лёгкий сервер (он слушает), потом
  мощный (он стучится) — иначе скрапер первое время будет получать
  ошибки соединения, пока не поднимется цель.
- **Первый скан каждой области** только наполняет базу и не пушит
  уведомления — эта защита в `storage.py` (`is_first_scan`), она общая
  для всех режимов, отдельно ничего настраивать не нужно.
- `API_TOKEN` обязателен и должен быть длинным случайным — порт 8080
  на лёгком сервере открыт всему интернету, без токена кто угодно
  сможет слать фейковые команды/уведомления через ваш бот.
- Сервис sberazs.ru построен на данных банка — использование строго
  в личных целях, без публичного распространения результатов.
